Thundering-herd protection for gRPC

When a thousand callers ask the same question, answer it once.

A Go sidecar that collapses identical in-flight gRPC requests into a single backend call. Envoy already load-balances, retries and reports on those requests — but it has no notion that they are the same request. This fills that gap.

Mechanism

Three paths, one backend call

Every request is reduced to a key — the gRPC method, the request payload, and any headers the operator has declared identity-bearing. That key decides which of three things happens, and only one of them touches the backend.

① Cache hit

A fresh result for this key is already held. Return it. The TTL is short by design — 100 ms — because its job is absorbing bursts, not being a cache.

45.7 ns/op · 0 allocations

② Join in flight

Someone is already asking. Block on the single channel the leader closes when it has an answer — no per-waiter registration, no polling, nothing to clean up.

waits on the backend · 0 allocations

③ Lead the call

Nobody has asked yet. Become the leader and call the backend on a context detached from your own, so one client hanging up cannot cancel work others are waiting on.

1,594 ns/op · 10 allocations

The follower path being allocation-free is the part worth stating precisely. Followers do not each register a channel to be notified on; they all wait on one channel the leader closes. The close/receive pair is what makes the result safe to read without a lock, and it means the cost of the thousandth caller joining a burst is the same as the second.

Design judgment

The dangerous default

Collapsing is only safe between requests whose responses are interchangeable — and method plus payload does not always establish that. Two callers can send byte-identical requests while authenticated as different users. Collapse those and one tenant is served the other tenant's data.

Naming the headers is the fix

Any header the backend varies its response by is declared, and becomes part of the collapse key. Those requests then get separate backend calls, and the burst protection still applies within each identity. 

COLLAPSER_KEY_HEADERS=authorization,x-tenant-id

Two related defaults fall out of the same reasoning. Backend errors are not cached, because one transient failure should not be replayed to every caller for the whole window. And liveness never depends on the backend — restarting the proxy during a backend outage would remove the very collapsing that is protecting it.

Built with

Stack

Schema-agnostic by design: a passthrough codec forwards raw gRPC frames unchanged, so the proxy needs no generated stubs and works in front of any protobuf service. One persistent client connection is shared across all backend calls, so HTTP/2 multiplexing does its job and there are no per-request handshakes.
